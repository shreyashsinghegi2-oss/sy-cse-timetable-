# StudentLancing opportunity AI and source rollout

The existing StudentLancing feeds, search, resume matching, internal listings, application flows, and response shapes remain in place. The opportunity AI engine uses Gemini for structured intent extraction, resume-profile extraction, and batched relevance ranking. Gemini receives compact candidate data and may only return supplied opportunity IDs. It cannot create or verify a listing. Career Compass remains a separate AI system. `STUDENTLANCING_AI_ENGINE` defaults to `gemini`; setting it to `legacy` selects deterministic, source-backed local ranking, **not** the old Claude/fabricated-listing code. Invalid values fail closed. This is a zero-Claude rollback path rather than a restoration of the unsafe old behavior.

## External-source status

External opportunities are shown only when a configured source is enabled and its access terms have been reviewed. For HTML sources, a listing detail page must be fetched and validated. For the official Himalayas JSON API, the returned structured job record, publication/expiry dates, provider update time, and same-origin job URL supply the evidence; the site itself is **not** scraped. The registry and parser live in `server/utils/lancing-sources.ts`; the API adapter is `server/utils/lancing-himalayas.ts`. Normalized records and source status use the `lancing_external_opportunities` and `lancing_external_source_metadata` Firestore collections. A disabled source's old cached records cannot be displayed. The recorded source URL points to an individual opportunity, not a search or category page. Expired, malformed, stale, and duplicate records are filtered by code, not by Gemini. A verified source record does not independently certify the employer.

**The Himalayas official remote-jobs API is enabled for India-eligible Jobs and Internships.** Its [API documentation](https://himalayas.app/docs/remote-jobs-api) and [publisher-maintained API repository](https://github.com/Himalayas-App/remote-jobs-api#attribution-and-terms-of-use) explicitly permit use on websites, including commercial use, with visible credit and a link to each original job; onward submission to third-party aggregators is prohibited. The site's [general terms](https://himalayas.app/terms) restrict automated website extraction, so the adapter uses only the documented JSON endpoint and **never fetches HTML job pages**. The API updates daily; the app syncs once a day, keeps records for at most 30 hours after a successful API check, and shows only unexpired India/unrestricted results. Students still apply on the original Himalayas page and only explicitly mark an external application as submitted afterward. The site shows Himalayas attribution on verified cards. The API is limited to remote jobs and internships; it does not provide microtasks or competitions.

The search endpoint's `updatedAt` may reflect the newest *matching posting* rather than the provider's daily refresh time. Quiet searches can therefore report an update several days old even while their listings have future expiry dates. The adapter rejects future or over-14-day-old snapshots and validates every record's posted date, category, allowed location, canonical source URL, and future expiry independently. A failed refresh is retried after five minutes rather than suppressing requests for a full day.

Internshala and Wellfound prohibit automated extraction in their terms; HackerEarth blocked the server probe. Unstop exposes public paths in robots.txt but its terms did not establish permission for automated extraction, and the tested detail page returned a generic application shell rather than usable listing details. These sources remain disabled. Microtasks remain internal-only and competitions remain empty unless another reviewed source supplies current records. Neither generated listings nor old hard-coded competition cards are used as substitutes.

The startup refresh and three-hour scheduler check for source updates. Himalayas has a 24-hour interval; disabled HTML sources retain their six- or twelve-hour schedules. Student requests read stored records; they never call the provider. Missing or failed sources yield an empty or still-fresh verified set, not invented results.

When a Jobs, Internships, Micro Tasks, Competitions, or AI Match view has no listings, it offers a separate **Explore the web** section. `POST /api/lancing/search-links` asks Gemini for short category-relevant *search phrases* (not listings, companies or URLs), and the server constructs Google search links from those phrases. Input categories and lengths are bounded, contact-like text is removed before sending terms to Gemini or building URLs, and links are never interpreted as verified opportunities or Apply actions. Provider failures use basic category-specific searches. Successful suggestions are cached for six hours; fallback suggestions are retried after five minutes. Simultaneous identical requests share one provider call. A separate Postgres-backed IP limiter allows 12 discovery requests/minute by default (`LANCING_SEARCH_LINKS_REQUESTS` can adjust it) without consuming the stricter opportunity-matching budget. This is a discovery aid, not an external listing feed or proof that an opening exists.

## API, authentication, and applications

`/api/match` requires a valid Firebase bearer token and uses the verified UID to load the profile; a different caller-supplied UID is rejected. Existing `/api/lancing/live-feed/:category`, `/api/lancing/search`, `/api/lancing/opportunities-hub`, and `/api/lancing/ai-match` response contracts remain available. Search covers internal listings and currently verified external records. Ranking caches are keyed by query, profile, and source dataset version; empty source sets skip Gemini. The frontend sends its Firebase token for authenticated matching. Public listing responses include only allowlisted posting fields, not raw employer records. Recruiter application lists require authenticated ownership.

Opening an external application page is **not** a submitted application and does not use an apply credit. After submitting on that external site, the student can explicitly select **Mark as Applied**. An authenticated, idempotent `POST /api/lancing/external-applications/mark-applied` writes the user's external application, and `GET /api/lancing/my-applications` returns their internal and external records. Internal applications continue through their in-platform apply route, including internship, microtask, and general-opportunity records. Existing apply-credit accounting is currently unlimited/no-op; confirmed external tracking therefore does not debit a credit. Do not describe opening a site as successful submission.

## Operations and limits

`GEMINI_API_KEY` is required server-side for Gemini processing. Without it, or when Gemini is unavailable, StudentLancing falls back to deterministic ranking of existing source-backed records; it does not generate opportunities. `GEMINI_MODEL` is optional and defaults to `gemini-3.5-flash-lite`, the model previously verified with this project's key; the suggested 3.1 Flash-Lite model was not reliably available here. Keys are never placed in browser code. Gemini operation logs record token usage, latency, dataset version/count, cache hit or miss, and success/failure. The API adds `fallback` and `engineStatus` without removing existing fields, and the UI identifies basic matching without exposing provider internals. Unpriced tokens are not turned into fabricated cost figures.

StudentLancing's separate Coding Arena coach, Placement Readiness learning path, placement-cell question generation, and assessment parsing/grading also use Gemini rather than Claude. Career Compass's own Claude-assisted roadmap implementation is deliberately unchanged.

No package installation or relational database migration is needed. Firestore source collections are created through the existing Admin SDK when an approved source is eventually enabled. Source data is deliberately not marked verified merely because an AI model mentioned it, a sitemap linked it, or a category page loaded.

## Verification before enabling external traffic

Before enabling the Himalayas source, the focused ranking/source suite passed 14 tests and the production build passed. A live Gemini ranking of 10 synthetic candidate IDs returned all 10 and no invented ID; telemetry recorded 557 input and 498 output tokens for that one call. The running app returned HTTP 401 for unauthenticated `/api/match` and external application POST/GET, and HTTP 200 with an empty, unverified-free result for public competitions, microtasks, and search in the then-current development data. The homepage preview loaded without a visible runtime error.

After enabling the API source on 2026-09-30, 43 focused tests and the build passed. The public development feed returned 15 verified, Himalayas-attributed Jobs and 15 Internships from the initial stored snapshot; Micro Tasks and Competitions remained empty, with no fabricated listings. The expanded bounded API adapter separately returned 20 valid unique records in each category; the next scheduled daily sync will update stored results. Live Gemini ranking succeeded on both public feeds. The existing TypeScript check still reports 105 unrelated errors. Authenticated applications and Career Compass save/reload were **not** exercised in this check.

The later search-links addition was tested against the running app: Gemini returned four safe web-search links for both competitions (79 input / 24 output tokens, 13.1 seconds) and jobs (79 input / 49 output tokens, 4.9 seconds); an identical jobs request hit the six-hour cache without another model call. These are search links, not verified individual openings. Missing, malformed, or unavailable model output returns clearly labeled basic searches instead.

Project-wide TypeScript checking still reports 105 pre-existing errors (including unreachable dashboard code); none are in the migrated server routes. Signed-in feed, resume match, internal apply, recruiter authorization, and external confirmation/save/reload were not exercised with test accounts. Once a permitted, accessible source is supplied, test its robots and terms, a real detail-page parse, expiry/staleness/deduplication, apply URL, refresh, and rate limits in an isolated environment. Do not claim the external source works from fixture tests alone.
